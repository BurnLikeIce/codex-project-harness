# 意图识别规则

当用户没有使用精确短口令，而是用自然语言表达时，使用这个文档。

这是意图识别，不是硬匹配。只要用户表达的意思接近下面某类意图，就按对应流程处理。

## 需求澄清

下面这些类似表达，都等价于 `新需求：...`：

- “我来和你讨论一下这个能不能做”
- “我有个想法”
- “这个功能能不能做”
- “这个值不值得做”
- “我们先聊一下这个方案”
- “帮我看看这个需求”

高置信度时，直接进入需求澄清。中低置信度时，先问一句简短确认。

## 新项目启动

下面这些类似表达，都表示用 project-harness 启动新项目，并让当前对话作为主控/集成对话：

- “按照 project-harness skill 开始新项目，这个作为主控”
- “用 project-harness 启动这个项目”
- “这个对话作为项目主控”
- “帮我初始化这个项目工作流”
- “给这个项目套上 harness”

高置信度时，安装/检查 harness 文件，检查 Git，并把当前对话作为主控。若需要初始化 Git 或配置 GitHub remote，而用户没有明确要求，先询问。

## 旧项目接管 / 迁移

下面这些类似表达，都表示按 `docs/migration.zh-CN.md` 迁移旧项目：

- “用 project-harness 接管这个旧项目”
- “迁移这个旧项目”
- “这个旧项目以后本对话作为主控”
- “把这个项目纳入 harness”
- “帮我整理成 project-harness 工作流”

高置信度时，先检查项目并输出迁移计划。用户确认前，不要覆盖已有文档，不要修改业务代码。

## 需求分发

下面这些类似表达，都等价于 `需求讨论结束，请分发任务。`：

- “好，就这么做”
- “按这个方案开始吧”
- “可以开干了”
- “安排一下”
- “拆一下任务”
- “让前端后端开始吧”

不要跳过任务文档和分发流程。产品对话必须先更新文档，再输出可直接复制给目标对话的任务指令。

## 问题分流

下面这些类似表达，都等价于 `问题：...`：

- “这里不对”
- “这个地方怪怪的”
- “为什么这里这样”
- “这个是不是 bug”
- “点了没反应”
- “这里显示不对”
- “我发现一个问题”

收到问题的对话应该按照 `docs/triage.zh-CN.md` 判断：直接修复、记录任务、升级产品、交给 Bugfix，或交给主控。

## 安全规则

如果意图不清楚：

- 不要静默开始实现。
- 先问一个简短确认问题。
- 给出最可能的选项，例如需求讨论、问题分流、直接小修。

如果用户说“开始吧”“按这个做”，但任务还没拆清楚，产品对话必须先做任务分发。

如果用户把问题发给了不完全对应的对话，收到问题的对话负责按 `docs/triage.zh-CN.md` 分流；用户不需要先判断应该找谁。
