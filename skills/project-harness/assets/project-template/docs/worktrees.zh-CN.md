# 分支和工作树管理

在判断某个对话应该共用当前工作目录、只创建分支，还是派生到新的 Git worktree 时，使用这个文档。

## 核心规则

- 分支是 Git 里的轻量指针，通常不怎么占空间。
- 工作树是本地真实文件夹，会占用磁盘空间，尤其包含 `node_modules`、构建产物、缓存或生成资源时。
- 主控/集成对话负责工作树策略、清理、集成和合并顺序。
- 产品和文档类对话默认使用主工作树。
- 前端、后端、Bugfix、实验对话在需要隔离时才使用独立工作树。

## 默认选择

这些情况使用同一工作树：

- 产品讨论和需求澄清。
- 只改文档。
- 不会和其他活跃任务冲突的小修复。
- 主控/集成的 review、合并、changelog 更新。

这些情况使用独立工作树：

- 前端和后端并行实现。
- 较大的功能开发。
- 有风险的重构。
- 实验和原型。
- 根因不明确或影响范围较大的 Bugfix。
- 任何可能和其他活跃对话冲突的任务。

## 各类对话默认规则

- 主控/集成：使用主工作树。
- 产品/架构：默认使用同一工作树，除非用户明确要求隔离文档工作。
- 前端：非小型功能默认使用独立工作树；很小的 UI 修复且没有并行冲突时可以同一工作树。
- 后端：涉及 API、schema、鉴权或服务端逻辑的非小型任务默认使用独立工作树。
- Bugfix：简单明确的小修复可以同一工作树；复杂调试或高风险修复使用独立工作树。
- 实验：使用独立工作树。

## 创建工作树前

主控/集成对话应先检查：

- 当前分支和工作区状态。
- 已存在的 worktrees。
- 该任务是否已经有活跃分支或工作树。
- 该任务是否小到可以留在当前工作树。
- 用户是否希望节省磁盘空间。

不要因为产品讨论、验收、文档协调而自动创建新的工作树。

## 命名

使用任务导向的分支名：

- `feature/fe-001-dashboard`
- `feature/be-001-api`
- `fix/bug-001-login`
- `experiment/editor-prototype`

工作树文件夹名尽量包含项目名或任务 ID，方便识别。

## 清理

主控/集成应定期询问是否盘点分支和工作树，尤其在合并之后。

清理流程：

1. 列出 branches 和 worktrees。
2. 判断哪些是主工作树、活跃任务工作树、已合并分支、过期分支、废弃实验。
3. 先输出清理建议。
4. 未经用户明确确认，不要删除分支或工作树文件夹。
5. 用户确认后，只清理明确确认过的过期工作树和分支。

## 可直接复制给主控的指令

```text
请按照最新 project-harness 的工作树规则，检查当前项目。

请列出当前 Git branches 和 worktrees，判断哪些是活跃、已合并、过期或可以清理的，并先给我清理建议。不要直接删除任何东西，等我明确确认后再执行。
```
