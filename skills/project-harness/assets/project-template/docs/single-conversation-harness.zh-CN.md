# 单主对话 Harness 工作模式

本文定义 project-harness 的默认轻量运行方式：一个长期主控/主产品对话可以承载产品讨论、任务规划、实现跟进、验收和发布决策。

专项对话、后台执行单元、分支和 worktree 仍然可用，但它们只是用于降低风险、隔离修改或并行推进的工具，不是每个任务都必须使用的流程。

## 核心原则

- 普通项目工作默认留在一个主控/主产品对话里完成。
- 同一对话内可以按阶段切换角色：产品、主控、实现、验收、发布、迁移。
- 文档仍是事实来源。重要产品决策、任务范围、验收标准、版本状态和发布决策必须写入项目文档。
- GitHub 推送、生产上线、生产数据库变更、删除 worktree、删除分支，必须由用户明确确认。
- 不要因为任务提到前端、后端、Bugfix 或验收，就默认创建专项对话或 worktree。

## 角色模式

主控对话可以明确进入这些模式：

- 产品模式：讨论用户场景、价值、范围、优先级、风险和验收标准。
- 主控模式：更新任务/决策文档，安排执行顺序，管理 Git 和发布闸门。
- 实现模式：在清晰任务边界内修改代码或文档。
- 验收模式：运行检查、查看页面或输出，并对照验收标准判断结果。
- 迁移模式：总结当前状态，方便新的主控对话接手。

进入实现、验收、发布或迁移前，先简短说明当前模式和即将执行的动作。

## 执行分级

小任务可以直接在主工作树顺序完成：

- 纯文档更新。
- 小范围文案或样式修改。
- 单文件或低风险修复。
- 产品验收后的记录更新。

中等任务仍可在主控对话中顺序执行，但开始前先说明：

- 任务范围。
- 预计涉及文件或模块。
- 验证方式。
- 回滚点。

并行或隔离任务可以使用后台执行单元、专项对话、分支或 worktree，但必须确实有帮助。

适合的任务：

- 只读代码调查。
- 小范围独立补丁。
- 用户继续讨论产品时，后台运行测试或构建。
- 不需要实时产品判断的任务。

不适合的任务：

- 需要实时产品决策的任务。
- 多个执行单元同时修改同一批文件。
- 生产发布、生产数据库变更、破坏性 Git 操作或 worktree 清理。

## Worktree 规则

worktree 是隔离工具，不等于必须新开对话。

- 不要为每个任务默认创建 worktree。
- 高风险、并行、冲突概率高或需要隔离验证时，才考虑 worktree。
- 创建前必须说明原因、路径、分支和预计清理方式，并等待用户确认。
- 任务结束后先给清理建议，不要自动删除。

## 文档闸门

单主对话模式不降低项目纪律：

1. 产品决策写入 `docs/decisions.md` 或相关产品文档。
2. 任务范围、负责人、依赖和验收标准写入 `docs/tasks.md`。
3. API 或数据结构变化写入 `docs/api-contract.md`。
4. 版本或发布状态写入项目的版本/changelog 文档，如果项目存在这些文档。
5. 长期协作方式变化写入 `HARNESS.md` 和本文。

## 主控迁移包

当主控对话上下文变长，或用户想迁移到新对话时，创建“主控迁移包”。

自然语言触发：

- “做一次主控迁移包”
- “准备迁移到新的主控对话”
- “总结当前主控状态”
- “写入主控迁移包”

默认行为：

- 用户说“做一次”或“准备”迁移包时，只在聊天中输出，不改文件。
- 用户明确说“写入”或“保存”迁移包时，更新 `docs/handovers/current-control-state.zh-CN.md` 或对应语言文件。

迁移包应包含：

- 当前工作模式。
- 项目路径。
- Git 状态。
- 当前版本或里程碑目标。
- 已完成任务。
- 正在进行的任务。
- 未提交改动。
- 关键决策。
- 安全边界。
- 下一步建议。
- 新主控对话启动提示词。

## 新主控对话启动

新的主控/主产品对话应先读取：

- `docs/handovers/current-control-state.zh-CN.md` 或对应语言文件。
- `HARNESS.md`。
- `docs/single-conversation-harness.zh-CN.md`。
- `docs/tasks.md`。
- `docs/decisions.md`。
- 项目内已有的版本、部署或本地开发文档。

启动时只做角色初始化和状态复述。除非用户明确要求，不要改代码、推送、上线或清理分支/worktree。
