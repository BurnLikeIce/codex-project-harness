# 问题分流规则

当用户用很短的话反馈问题时，使用这个文档，例如：

```text
问题：<描述>
```

收到问题的对话必须先判断问题类型，然后选择：直接处理、记录任务、或输出可复制给其他对话的升级指令。

## 分流规则

- 明确、较小、归属清楚的实现问题：交给对应实现对话，例如前端或后端。
- 不确定是不是 bug、涉及产品行为、交互规则、范围或验收标准：交给产品/架构对话澄清。
- 根因不明、跨前后端、回归问题、测试失败、build/CI/部署失败：交给 Bugfix/CI 或主控。
- 分支、合并、PR、发布、环境、部署协调问题：交给主控对话。

## 记录规则

不要让修复消失在聊天里。

- 如果问题属于已有任务，记录到 `docs/tasks.md` 的对应任务下。
- 如果是任务外的小修复，创建一个小任务，例如 `BUG-001` 或 `FE-001`。
- 如果问题比较大或不明确，不要直接实现；先输出可复制给产品或 Bugfix 对话的澄清/拆分指令。

## 收到问题后的输出

收到 `问题：<描述>` 后，对话应该输出下面四类之一：

```text
分类：可直接修复
原因：
任务记录：
下一步：
```

```text
分类：需要产品澄清
原因：
可直接复制给产品对话的指令：
...
```

```text
分类：需要 Bugfix 排查
原因：
可直接复制给 Bugfix 对话的指令：
...
```

```text
分类：需要主控协调
原因：
可直接复制给主控对话的指令：
...
```
